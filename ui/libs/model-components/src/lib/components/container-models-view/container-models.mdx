# Container Models

A container is KOS's collection: a reactive, indexed, lifecycle-aware set of
models. `@kosContainerAware` adds one to a model and injects the methods that
add and remove members, so the model owns its collection and the events that
change it.

`team` owns `user` models. The team creates them, adds them, removes and
destroys them; no code outside the team modifies the collection.

## Try it

<Canvas of={Stories.ContainerModelsStory} sourceState="none" />

Press **add member** and a user is built and added to the team; **remove last**
takes the newest one out. The list is the container's `data` array, read by
the view.

## How it was built

**Scaffold both models.** The parent-and-child page covers `--parentAware`.

```bash
kosui model --name team --project core-concept-models
kosui model --name user --project core-concept-models --parentAware
```

**Put the container on the team.** The team is the concept that owns the collection,
so the decorator goes on `team` itself. The command writes `@kosContainerAware<UserModel>()`
above the class, adds `KosContainerAware<UserModel>` to the merged interface and imports
the child type; the two sections after this one show the result.

```bash
kosui model:add-container --modelName team --project core-concept-models --childModel user
```

`kosui model --container` and `kosui model:container` build the other shape: a separate
`<model>-container` model that manages the collection without being a new concept. The
Dedicated Container Model page builds that shape.

**Own a single child too.** A single child on `team`: property `lead`, child `UserModel`.

**Register, hooks, component.** Register `team` and `user` in the app's registration chain.

```bash
kosui model:hook --modelName team --project model-components
kosui model:hook --modelName user --project model-components
kosui component --name container-models-view --project model-components
```

## The decorator

`@kosContainerAware<Child>()` sits on the class, with no options; every
option has a default. The journal's container is the bare form. The
container's parent id is the owning model's own id, so each child's lifecycle
is tied to its owner's. The decorator injects the container and a surface for
working it:

- `container`, the container itself, and `data`, the reactive array of its
  models. `models` is a second name for the container.
- `getModel(id)`, `addModel(model)`, `removeModel(id)`, `addAll(models)` and
  `removeAll(ids)`. `removeModel` takes a model out of the container and
  leaves it alive.
- `removeAndDestroy(id)` and `removeAndDestroyAll(ids)`, which remove a model
  and then destroy it.

## Migration and naming options

The remaining options rename or trim what the decorator injects. They exist
for code written before the decorator, where callers already read the
container under another name. A new model leaves them out. `document` carries
them, since its code reads `this.notes`:

- `containerProperty` renames the container (`notes`). The merged interface
  then uses `KosContainerAwareWithProp<NoteModel, 'notes'>` in place of
  `KosContainerAware<NoteModel>`, so the compiler knows the name.
- `modelsProperty` renames the `models` getter (`noteList`).
- `includeMethods` and `includeGetters` default to `true` and are only worth
  writing as `false`, for a class that declares its own methods or getters
  under the same names. The codex does not set them.
- `containerOptions.extensionId` names the container to the extension
  manager. An index extension registered under that id contributes its
  indexes to the container.
