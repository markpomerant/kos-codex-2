# Model Lifecycle Race Conditions

A collection is a baseline plus deltas: a LOAD request establishes the state,
and topic events amend it as other clients and the device change things. A
event can arrive before the handler has subscribed, while the baseline request
is in flight, or before the request was sent, and each case does something
different to the model.

In most models the baseline is isolated from the topics, or a delta carries
enough context to be applied on its own, and the collection converges without
these options. Use the options on this page when a delta cannot be applied
safely without its baseline. The timelines below show the four cases and what
`lifecycle`, `requiresBaseline` and `replay` do to each.

<RaceTimelines />

The `journal` model holds notes the codex backend publishes on its object
topics, `/studio/codex/objects/added` and `/removed`. Those events are
out-of-band events: another client changed the list, and the topic delivers
the change to this model. Topic handlers exist for these events. The model's
own requests apply their responses; they do not wait for a topic.

## How it was built

**The model.** Scaffold `journal` and make it a container of notes, then add the two
counters as model properties.

```bash
kosui model --name journal --project core-concept-models
kosui model:add-container --modelName journal --project core-concept-models --childModel note
```

**The baseline.** `--lifecycle LOAD` runs the request when the model loads.

```bash
kosui model:add-service-request --modelName journal --project core-concept-models \
  --methodName onNotesLoaded --servicePath /api/codex/test/objects/race --method get --lifecycle LOAD
```

**The handlers.** Add a topic handler on `journal` twice, on the backend's `added` and `removed` topics; `requiresBaseline` and `replay` are added to the decorators.

**The device side.** The `device` model's `addObject` and `removeObject` requests (POST `/api/codex/test/objects/added` and `/api/codex/test/objects/removed`) ask the backend to add or remove a note out of band.

## A baseline that races its own delta (case B, on demand)

The backend serves the journal's baseline from a test endpoint built for this
page: it adds a note, publishes it on the `added` topic, waits, and then
answers with the list. Every load of a journal therefore sees a delta arrive
while its baseline request is still in flight, which is case B. The options
below handle it.

## The subscription

The handler is an ordinary websocket topic handler on the `added` topic. It
registers at `INIT`, so the subscription exists before the LOAD request goes
out. With the default registration the subscription would be made after the
event had already passed. `lifecycle` is the one option here that departs from
the Topic Handlers opener, and it is what the page is about.

<Snippet name="topic-catch-up@journal-model.ts" />

## requiresBaseline

`path` and `method` name the lifecycle request whose response is the
baseline. Until it has answered, events on the topic are queued; then they
are replayed according to `replayStrategy`: `AFTER_REQUEST` keeps events
that arrived after the request was sent, `AFTER_RESPONSE` only those after
the response, `ALL` everything, `NONE` discards the queue.

<Snippet name="topic-requires-baseline@journal-model.ts" />

## replay

`replay.bufferSize` asks the event bus to keep the last events on the topic,
for handlers that subscribe later. In this exemplar the `requiresBaseline`
queue carries the early event; the replay buffer was not observed to deliver
anything on its own.

<Snippet name="topic-replay@journal-model.ts" />

## The handlers

An `added` event carries the note as stored; the handler counts it and
updates the existing note in place or builds a new one. A `removed` event
drops the model. Both run after the baseline has been applied.
