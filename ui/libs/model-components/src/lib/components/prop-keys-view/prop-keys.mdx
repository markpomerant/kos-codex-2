# Prop Keys

A decorator option is written once, on the class, and every instance of the
model shares it. A PropKey makes such an option read a value from the instance
instead. It is a placeholder string the framework replaces with a model
property at the moment the option is used: when a topic is subscribed, when a
service request is sent, or when a dependency is resolved. The property can be
plain state or a computed property.

Two forms exist:

- `{MODEL_ID}` is replaced with the instance's id.
- `createPropKey<Model>('name')` produces `{PROP_name}`, which is replaced
  with `instance.name`. The type argument checks that the property exists.

## How it was built

**The computed property.** Add `zone` as a computed model property of `widget`,
derived from the id.

**The handlers.** Add two topic handlers on `widget`: `onOwnReading` on
`/codex/widget/{MODEL_ID}/reading`, and `onZoneStatus` on a topic constant built with
`createPropKey`.

**The dependency.** Add `teamKey` as a model property of `project`, then change the
`id` of the existing dependency on `project` to
`createPropKey<ProjectModelImpl>('teamKey')`.

**The counters.** Add `ownReadings` and `zoneEvents` as model properties of `widget`.

## Where a PropKey is substituted

| Option | Decorator | Source of the value |
| ------ | --------- | ------------------- |
| `topic`, `destinationAddress` | `@kosTopicHandler` | the instance, when the subscription is made |
| `path`, `pathParams`, `queryParams` | `@kosServiceRequest` | the instance, when the request is sent |
| `id`, `options` | `@kosDependency` | the instance, when the dependency is resolved |
| `path` | `@kosConfigProperty` | the instance, since the config property is a dependency whose options carry the path |

## A topic per instance

`{MODEL_ID}` in a topic gives every widget its own subscription. A message
published for `widget-north` reaches that widget only.

## A topic from a computed property

`zone` is a computed property. The topic constant embeds
`createPropKey<WidgetModelImpl>('zone')`, so the subscription is made on
`/codex/zone/north/status` for `widget-north` and on `/codex/zone/south/status`
for `widget-south`. Any model property works here, including one derived from
options or from other state.

## A dependency chosen by the instance

The project's team is resolved by id. With a PropKey as the id, the id is
read from the project's `teamKey` property when the dependency is resolved,
so two projects can depend on two different teams from one decorator.

## Service requests

The same substitution applies to a request's `path`, `pathParams` and
`queryParams`. With the typed `serviceRequest` form the parameter types come
from the API spec, so a PropKey string is accepted where the parameter is a
string. The codex backend's object ids are integers, so this page shows the
mechanism on topics and dependencies.
