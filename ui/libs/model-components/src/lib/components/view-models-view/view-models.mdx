# View Models

UI state, such as which unit a panel shows, which row is expanded, or whether
a warning is dismissed, lives in a ViewModel, separate from the data model. `@kosViewModel` makes a plain class reactive the way
a data model is, without registering it or putting it in the model graph.
`typeId` names it. Everything else on the decorator has a default.

A component creates one with `useViewModel`, giving it the data models it
reads from; the instance lives as long as the component.

## How it was built

**The class.** One command writes the ViewModel beside the models it reads, with
`@kosViewModel`, `@kosLoggerAware`, the interface merge and a constructor that takes the
`widget` model. `--models` accepts a comma-separated list; each becomes a constructor
parameter, in order.

```bash
kosui model:view-model --name widget-temperature --project core-concept-models --models widget
```

**The state.** A `unit` field added to the class.

**The computed values.** `display` and `isHot`, read from the data model and the unit.

**The action.** `toggleUnit`, which changes only ViewModel state.

**The component.**

```bash
kosui component --name view-models-view --project model-components
```

## The decorator

`@kosViewModel` makes the class's fields model properties and its getters computed properties,
the way `@kosModel` does for a data model. `typeId` names the class in logs
and in the dev tools; it defaults to the class name, and is written here so the
name survives a minified build. `@kosLoggerAware` adds a `logger`, as on a
model.

## The state and the data model it reads

The ViewModel owns one piece of UI state, the unit to show. The data model
